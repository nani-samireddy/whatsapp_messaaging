# WhatsApp Messaging: review and inbox design

Reviewed 18 October 2026 (Asia/Kolkata). Baseline scope: review, design, and planning only.

After this review was saved, the user authorized local implementation in a separate app project. See [implementation progress](../../IMPLEMENTATION-PROGRESS.md) for subsequent changes and validation; the findings below refer to the pinned baseline revision.

## Recommendation

Do not enable this revision for business messaging yet. It is an outbound text/media automation prototype with local templates, rather than an inbox or a complete WhatsApp Cloud API integration. Before adding a polished inbox, close the send authorization and credential exposure paths and introduce durable message/outbox records. Then build one complete receive → display → reply → delivery-status path on that foundation.

The existing Conversation, Phone Number, Media, and local Template concepts are useful. Their current identity, permissions, and message storage need changes. Reuse the names where practical; do not extend the conversation child table into the permanent message store.

## What the app actually does

| Workflow | Actual route and behavior | Main limitation |
|---|---|---|
| Manual send from a Frappe document | Desk bundle calls `get_template_doctypes` once at app readiness; every matching form gets template buttons. Button calls `wm_handle_on_custom_trigger(template_name, doctype, docname)`, loads both documents, renders text, gathers recipients, optionally builds media, then posts synchronously. | No server send authorization, filter/event/disable checks, preview, idempotency, or structured result. Buttons include all template event types. |
| “Is Single” / bulk send | Template form's Send Message button calls `wm_handle_on_single_template_trigger`; `process_template_query` enumerates *all matching documents* and sends to each document's recipients serially in the request. | “Single” means manual query trigger here, not one recipient. The same static recipient can receive one copy for every source document. No campaign/per-recipient run record, progress, cancellation, pagination, or backpressure. |
| Document events | Wildcard hooks map after-insert, update, delete, submit, cancel to Create/Update/Update Field/Delete/Submit/Cancel. Matching non-single templates are fetched and the document plus template snapshots are queued. | Queue publication precedes transaction commit; stored filter JSON is passed directly to the evaluator; one exception can stop remaining templates. |
| Scheduled and recurring | Template controller creates a Scheduled Job Type whose Python method embeds a base64 template name. Dynamic module `__getattr__` reconstructs the callable. A run queries documents and sends; Scheduled then stops its job and marks Completed. Cron runs recur. | New-record naming lifecycle, no durable run/recipient state, yearless one-shot cron, incomplete stop/resume/edit/delete handling, false completion. `tasks/cron` duplicates the scheduler shim but the generated path uses `tasks/scheduler`. |
| Local templates | JS field picker inserts `{{section.field}}`; `parse_message` substitutes attributes from the source document and linked template documents. | Local text expansion is unrelated to approved Meta templates; no language, approval, category, or component parameter model. |
| Recipients | Primary number comes from a configured source field. Other recipients are Table MultiSelect rows linking Static Recipient. Formatting strips leading `+` and hyphens, then deduplicates within that one document. | Linked-recipient lookup uses the child object instead of its link value; weak phone parsing; no consent/suppression/recipient run ledger. Static Recipient has System Manager permissions only. |
| Phone accounts / settings | Phone record supplies Meta phone-number ID and access token; global settings supply URL and version. | Token is Data, not Password; no WABA/portfolio identity, account membership, health, enabled flag, or unique external phone ID. Defaults to expired Graph v19.0. |
| Media | Every new WhatsApp Media record enqueues upload. Upload reads the file, guesses MIME, uses account token, stores provider ID in the same field as loading/error strings. Send chooses URL or uploaded ID. | Upload also runs for URL records, can race commit, edits do not reupload, no ready/expiry/account validation, captions added to every type. |
| Conversation and logging | After a POST, logger finds/creates a Conversation by recipient alone and appends/inserts/saves/submits a Conversation Field child. | No sender account/provider ID, no inbound receiver, no delivery/read callbacks, no safe concurrent upsert; log child direction is left empty. |
| Standalone Message and Message Log | Both have passive `Document` controllers; no sending workflow uses them. Logger writes Conversation Field instead. | Message is currently an unused draft-like schema; Message Log is not the actual send log. Workspace only links Templates, Media, Phone Numbers, and declares `app: hms`. |

## Confirmed findings and concrete fixes

Priority: **P1 High** = fix before enabling real messaging; **P2 Medium** = necessary for reliable inbox/automation; **P3 Low** = usability/maintenance. These are source-confirmed defects or missing controls. Failure scenarios describe what happens when the relevant path/configuration is used; they are not claims that production has already been exploited.

### Security and authorization

**F01 — P1 High: authenticated callers can invoke sends without the intended roles or source-record permissions.** [C:32–68](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/controller.py#L32-L68), [C:92–103](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/controller.py#L92-L103). Both whitelisted send methods use unrestricted `get_doc`; bulk uses permission-bypassing `get_all`. There are no explicit role, account, template, or source read checks, nor template-doctype consistency checks. A logged-in user who knows names can trigger an existing template against an unreadable record, or run an unbounded bulk query. Whitelisting authenticates callers; it does not authorize these operations. Fix with one server send service that checks role, account membership, template visibility, source read and permitted field mappings, template/source type agreement, and separate bulk permission. Reject before any provider call or job creation. Make mutation endpoints POST-only.

**F02 — P1 High: template rendering can expose account credentials.** [C:209–243,253–266](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/controller.py#L209-L266), [Template permissions:242–252](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/whatsapp_messaging/doctype/whatsapp_message_template/whatsapp_message_template.json#L242-L252). A Whatsapp Editor can write `message_preview` through document APIs despite the form's read-only field. `{{phone_number_id.access_token}}` resolves through an unrestricted linked-account read and becomes outgoing message text. An offline dummy-value probe confirmed interpolation. Hiding this field in the picker would not fix the server renderer. Replace arbitrary attribute access with an allowlisted mapping of readable business fields; never put account/settings/job documents in rendering context. Reject Password, secret, private/internal and non-approved fields. Review historical templates/logs and rotate any token if exposure is found when credentials are introduced or during a later authorized audit.

**F03 — P1 High: token stored as plain Data and outbound host is unrestricted.** [Phone JSON:21–27,48–60](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/whatsapp_messaging/doctype/whatsapp_phone_number_id/whatsapp_phone_number_id.json#L21-L60), [config:14–30,45–53](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/utils/config.py#L14-L53), [Settings permissions:54–62](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/whatsapp_messaging/doctype/whatsapp_settings/whatsapp_settings.json#L54-L62). `print_hide` does not encrypt or mask an API-returned Data field. Moreover Whatsapp Admin can change the API URL even though only System Manager can read phone accounts: a subsequent send forwards the token to that URL. Use Password storage and server-only `get_password`, separate non-secret phone metadata from credentials, restrict credential administration, and allow only the expected HTTPS Graph host/path/version. Disable redirects that could forward bearer credentials. Never return tokens in previews, job payloads, events, errors, or exports.

**F04 — P2 Medium: metadata endpoints exceed their required access.** [U:7–29,122–143,157–231](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/utils/__init__.py#L7-L231). `get_doctype_fields` is guest-enabled, reads arbitrary named documents, and returns schema metadata of linked/selected types without checking read permission. This endpoint returns field definitions, **not arbitrary document values**. `get_input_fields` includes Password fields by default; template discovery uses `get_all` and a shared site cache without user filtering. Remove guest access, authorize metadata reads, exclude sensitive/internal fields, and filter cached template metadata for each caller before returning it.

**F05 — P2 Medium: coarse DocType roles allow message-history alteration and cross-account access.** [Conversation JSON:38–74](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/whatsapp_messaging/doctype/whatsapp_conversation/whatsapp_conversation.json#L38-L74), [hooks:112–122](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/hooks.py#L112-L122). Editors can create/write/delete/share/export every conversation; there are no account/assignment permission hooks. A support agent could change history or read another team's messages. Introduce account membership and row-level checks, server-written immutable message records, restricted export/deletion, and independently permissioned business-record links. Apply the same rules to list/detail, generic resource APIs, search, files, and realtime subscriptions.

### Message correctness and durability

**F06 — P1 High: local templates do not send approved-template messages and no service-window rule is enforced.** [C:124–155](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/controller.py#L124-L155), [Template schema:36–88](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/whatsapp_messaging/doctype/whatsapp_message_template/whatsapp_message_template.json#L36-L88). Payload type is text or media; the selected template_type is ignored. There is no `type: template`, approved name/language/components or inbound-window data. A scheduled appointment reminder outside the customer-service window is sent as free text and can fail. Separate local automation rules from approved Meta templates. Validate exact named/positional parameter mappings, component counts/types and language; recheck approval and window immediately before dispatch. Do not silently convert invalid templates to text.

**F07 — P1 High: external sends are not tied safely to database transactions.** [C:88,100–103](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/controller.py#L88-L103), [Media controller hook:21–27](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/whatsapp_messaging/doctype/whatsapp_media/whatsapp_media.py#L21-L27), [send:29–42](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/utils/message_controller.py#L29-L42). Document/media jobs enqueue with Frappe's default `enqueue_after_commit=False`. A worker can send for a transaction that later rolls back, or fail reading an uncommitted media record. Manual/bulk requests also perform HTTP before their local logging transaction commits. Persist send intents in the source transaction, enqueue after commit, and use a database sweeper so a committed intent survives Redis publication failure. Workers receive IDs, not credentials or mutable full documents.

**F08 — P1 High: no durable idempotency or ambiguous-send handling.** [bulk:44–64](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/utils/message_controller.py#L44-L64), [C:100–103,155–158](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/controller.py#L100-L158). Double-clicks, repeated HTTP requests, repeated events, or rerunning partially successful batches resend already accepted messages. A timeout after provider acceptance is recorded Failed and invites a duplicate retry. Add unique logical send keys, per-recipient intents/attempts, worker leases, and Unknown outcome. Do not automatically retry a POST whose acceptance is uncertain. Local deduplication cannot guarantee exactly-once delivery across an external API without a documented provider idempotency guarantee.

**F09 — P2 Medium: provider acceptance is logged as Sent and the provider ID is discarded.** [send:32–42](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/utils/message_controller.py#L32-L42), [logger:5–30](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/utils/log_manager.py#L5-L30). Presence of `messages` is treated as Sent without retaining `wamid` or acceptance/hold details. A later failed delivery remains Sent forever. There is no webhook receiver anywhere in the app. Persist acceptance separately; update sent/delivered/read/failed from signed status callbacks correlated by sender account and provider ID. A successful POST is not evidence of delivery or reading.

**F10 — P2 Medium: account identity and log structure lose essential facts.** [logger:9–30](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/utils/log_manager.py#L9-L30), [Conversation schema:4–27](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/whatsapp_messaging/doctype/whatsapp_conversation/whatsapp_conversation.json#L4-L27), [child schema:18–76](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/whatsapp_messaging/doctype/whatsapp_conversation_field/whatsapp_conversation_field.json#L18-L76). Messages to one recipient from two business phones merge into one recipient-named conversation. Logger supplies a nonexistent parent status field and child recipient field, leaves the child's `from` blank, and has no provider ID or source record. Its exists-then-insert is also racy under concurrent first sends. Replace child logging with immutable messages and unique account/peer conversations. The child's unusual direct insert/save/submit sequence warrants runtime regression testing; this review does **not** claim that submission necessarily throws on Frappe 16.

**F11 — P2 Medium: network operations have no explicit timeout or recovery policy.** [send:32–42](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/utils/message_controller.py#L32-L42), [upload:34–46](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/utils/media_controller.py#L34-L46). Frappe 16.52.0's integration helper defaults to `timeout=None`; the app supplies none. Exceptions are broadly caught and lose structured Meta errors; queue/job termination is not a network recovery strategy. Set connect/read deadlines, classify validation/auth/rate-limit/provider errors, honor retry guidance, use bounded jittered backoff where a retry is safe, and show dead-letter/unknown states with redacted diagnostic codes.

### Recipients, templates, scheduling, and UI

**F12 — P2 Medium: static recipient resolution is wrong.** [C:170–192](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/controller.py#L170-L192), [link schema:12–16](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/whatsapp_messaging/doctype/static_recipient_link/static_recipient_link.json#L12-L16). `get_value("Static Recipient", row, "phone_number")` passes a child Document, not `row.static_recipient`. Frappe's query builder rejects unsupported filter objects; the catch returns `[]`, dropping even an already collected primary number. Resolve the linked name, check permitted recipients, and report invalid rows individually. Remove full recipient lists from Error Log (`C:187`).

**F13 — P2 Medium: phone handling is not normalization or validation.** [U:100–120](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/utils/__init__.py#L100-L120). Spaces, parentheses, local-number ambiguity, extensions, invalid types and invalid lengths pass through or become None. Formatting variants evade deduplication. Parse with an explicit region when needed, store E.164 plus original input, reject ambiguity, and derive provider wire format separately. Keep Meta peer IDs opaque; current Meta BSUIDs are not phone numbers (see API rules).

**F14 — P1 High: Disable and manual event restrictions are not enforced.** [Template disable:168–173](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/whatsapp_messaging/doctype/whatsapp_message_template/whatsapp_message_template.json#L168-L173), [C:32–158](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/controller.py#L32-L158), [U:129–138](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/utils/__init__.py#L129-L138). No send/discovery query reads `disable`. A user disables a bad reminder, but events, cron and manual buttons still send it. Custom send also bypasses configured query filters. Enforce enabled/event/eligibility centrally at intent creation and dispatch; distinguish explicit manual override as a separately authorized action. A global dispatch kill switch must stop new attempts without deleting queued work.

**F15 — P2 Medium: filtered document-event sends fail.** [C:109–115](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/controller.py#L109-L115), [U:145–154](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/utils/__init__.py#L145-L154), [JS:289–296](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/whatsapp_messaging/doctype/whatsapp_message_template/whatsapp_message_template.js#L289-L296). UI stores a JSON envelope string; event evaluator expects filter tuples/mapping, not that string. Frappe's Filters constructor rejects the long string. The outer catch ends remaining template processing. Parse and validate one canonical filter representation for both query and event paths; use a JSON/Long Text field rather than Data for variable-length filters. Capture changed-field facts before enqueue: `_doc_before_save` is absent on first insertion and should not be assumed to survive all event contexts.

**F16 — P2 Medium: scheduled job identity is created before final template naming.** [template controller:19–26,54–64](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/whatsapp_messaging/doctype/whatsapp_message_template/whatsapp_message_template.py#L19-L64), [U:71–82](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/utils/__init__.py#L71-L82). Frappe runs before_insert before set_new_name. A new API-created scheduled template with no name reaches `None.encode`; a temporary client name can instead be baked into the method and later fail to find the final template. Create schedules after durable naming, preferably via one fixed dispatcher over schedule rows. Validate role-aware schedule creation without granting agents arbitrary Scheduled Job Type administration.

**F17 — P2 Medium: one-shot schedule and completion states are unreliable.** [U:55–69](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/utils/__init__.py#L55-L69), [C:11–30,94–95,157–158](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/controller.py#L11-L158), [template controller:45–71](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/whatsapp_messaging/doctype/whatsapp_message_template/whatsapp_message_template.py#L45-L71). Cron loses year/seconds; missed occurrences have no catch-up policy. Completed is set regardless of recipient outcomes. An unchanged cron expression does not restart a stopped job; switching away from Scheduled/Cron or deleting/renaming a template has no job cleanup. Cron assigns `self.status` although the schema field is `schedule_status`. Use UTC due_at, explicit timezone and recurrence policy, atomic due-run claims, per-run keys and outcomes, pause/resume/cancel, and a tested missed-run rule. “Completed” must mean expansion finished with explicit counts, distinct from delivery success.

**F18 — P2 Medium: media lifecycle produces invalid or stale sends.** [Media hook:15–27](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/whatsapp_messaging/doctype/whatsapp_media/whatsapp_media.py#L15-L27), [media utility:10–78](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/utils/media_controller.py#L10-L78), [C:134–148](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/controller.py#L134-L148). URL records still enter the upload/file-read path. Exceptions before its try are unhandled; editing an attachment never reuploads. Sends accept loading/error/expired IDs and another account's media. Audio/sticker payloads get unsupported captions; all media captions overwrite the saved media caption with parsed template text. MIME is guessed from extension without type/size checks. Split storage from upload state, validate type-specific payloads and files, bind uploads to account/file hash, refresh expired media, and block sends until ready. Prefer uploaded IDs for private LAN files.

**F19 — P2 Medium: bulk runs and UI conceal failures.** [C:40–48,59–68,100–103](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/controller.py#L40-L103), [buttons:30–59](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/public/js/custom_buttons.js#L30-L59). Exceptions become Error Log entries and RPC methods return None on both success and failure; JS expects `response.message`. Large queries block a web worker and may be retried by a user after timeout. Return a durable request/run ID immediately, show queued/accepted/failed/unknown per recipient and truthful aggregate counts, paginate expansion, and cap/scope bulk permissions. Preserve structured errors, not token-bearing bodies.

**F20 — P2 Medium: default API version is expired.** [Settings JSON:18–24](https://github.com/nani-samireddy/whatsapp_messaaging/blob/d55395fe92f576287c3a1a1778e135bf3e21f9d5/whatsapp_messaging/whatsapp_messaging/doctype/whatsapp_settings/whatsapp_settings.json#L18-L24). v19.0 was available only until 21 May 2026 per Meta's official changelog. ## Current WhatsApp rules and design consequences

1. **Public HTTPS and webhook verification:** Meta requires a public GET/POST endpoint with a valid trusted certificate; self-signed certificates are unsupported. Validate GET mode/token and return the raw challenge with HTTP 200. For POST, verify `X-Hub-Signature-256` using HMAC-SHA256 over the original body and the app secret, with constant-time comparison. Verification token, app secret, and send access token have separate purposes. Persist authenticated events before acknowledging them; a standard Frappe JSON `{"message": ...}` challenge wrapper is insufficient. Meta provides no API for historical webhook replay. [Meta: create endpoint](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/create-webhook-endpoint)
2. **Retries and routing:** non-200 or undeliverable callbacks can be retried for up to seven days, with duplicates. Subscribe the app to the WABA and the `messages` field. Payloads may contain multiple entries, changes and updates; process all supported elements, not only index zero. Route using WABA and `metadata.phone_number_id`. [Meta: webhook overview](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/overview), [Meta-owned subscription guide](https://www.postman.com/meta/whatsapp-business-platform/folder/ozgs3jn/webhook-subscriptions)
3. **Service window:** ordinary free-form service messages are allowed during the 24-hour customer-service window; a subsequent user message resets it. Current documentation also describes qualifying calls. This MVP uses authenticated inbound messages as its window source; calling is outside scope. Outside the window, use an approved template. Compute from provider occurrence time, not webhook arrival/retry time; outbound messages and templates do not reset this timer. Do not label service messages as universally free: current pricing documentation must govern any cost display. [Meta: service messages](https://developers.facebook.com/documentation/business-messaging/whatsapp/messages/send-messages)
4. **Approved templates:** sending requires the approved template identity and language plus exact typed component parameters. Positional parameters preserve order; named parameters supply `parameter_name`. Approval can change, so local saved text alone cannot authorize sending. Preserve immutable sent-template/mapping snapshots. [Meta: template fundamentals](https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/overview), [components](https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/components)
5. **Acceptance and receipts:** send responses carry provider IDs and may indicate acceptance or a quality hold. Incoming messages are in `messages[]`; outgoing receipts are in `statuses[]`. Keep accepted distinct from sent/delivered/read/failed. A read receipt can imply delivery without a separate delivered event. Retain error events and allow unknown/extra status values, including played for supported voice messages. The provider's pricing `conversation.id` is not a stable CRM conversation key and can be omitted in newer versions. [Meta: Messages API](https://developers.facebook.com/documentation/business-messaging/whatsapp/reference/whatsapp-business-phone-number/message-api), [webhook structures](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/reference/messages), [statuses](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/reference/messages/status)
6. **Media:** support provider upload IDs or fetchable hosted media; private LAN URLs cannot be fetched by Meta. Current documented limits include images 5 MB, audio/video 16 MB, documents 100 MB, and distinct sticker limits/codecs. Media URLs expire after five minutes; uploaded IDs expire after 30 days and webhook media IDs after seven days. Retrieve/download with server credentials and store private files; never expose bearer tokens or temporary provider URLs to browsers. Validate the selected supported types against the pinned API contract. Captions apply only to types that support them. [Meta: media](https://developers.facebook.com/documentation/business-messaging/whatsapp/business-phone-numbers/media), [audio payload](https://developers.facebook.com/documentation/business-messaging/whatsapp/messages/audio-messages), [sticker payload](https://developers.facebook.com/documentation/business-messaging/whatsapp/messages/sticker-messages)
7. **Identity has changed:** Meta's 2026 BSUID rollout means phone numbers may be omitted from inbound webhooks. Store an opaque portfolio-scoped `user_id`/`recipient_user_id` and identity aliases; never run it through E.164 parsing. Username is a display attribute, not a permanent identity key. Support phone-only legacy records and safe linking when Meta supplies both identities. Test actual enabled account/version payloads before go-live. [Meta: business-scoped user IDs](https://developers.facebook.com/documentation/business-messaging/whatsapp/business-scoped-user-ids)
8. **Version:** v19.0 expired 21 May 2026. Meta lists v26.0 and v25.0 among newer versions on the review date; choose one supported version after contract tests rather than blindly replacing a string. [Meta: Graph versions](https://developers.facebook.com/docs/graph-api/changelog/versions), [v19.0 lifecycle](https://developers.facebook.com/docs/graph-api/changelog/version19.0)

### MVP layout and everyday workflow

Use a Frappe Desk page `/app/whatsapp-inbox`, reachable from the WhatsApp workspace and a “View conversation” action on permitted business records. Keep a stable three-column desktop layout:

The design preview accompanying this review contains fictional examples and local interactions only. It does not connect to Frappe or Meta.

- **Read and triage:** choose a business phone or All permitted phones; search name/number/username; filter Mine, Unassigned, Unread, status. Rows always show the business phone to prevent replies from the wrong number. Cursor pagination sorts by latest activity and a stable tie-breaker. Select a conversation, load the newest message page, and fetch older pages on demand.
- **Unread:** per-agent read cursors, not one global boolean. Mark read only through the last visible inbound sequence; a concurrently arriving message remains unread. Local read state does not automatically mark the message read on WhatsApp. Remote read receipts should be a separate explicit setting/action with its own outbox action if later enabled.
- **Assignment and status:** assign to an authorized agent, take ownership, or return to queue; change Open → Pending → Resolved. Inbound messages reopen resolved conversations by the proposed default. These workflow states are distinct from provider delivery states. Use version checks to avoid overwriting another agent's concurrent changes; show a compact “updated by another agent” notice and refresh.
- **Reply:** header fixes the sender phone. Reply mode offers plain text and validated attachment types only when the service window is open. Expired/unknown window disables free-text submission and offers approved templates, preserving the draft. Revalidate the window at dispatch, since it can expire while queued. Keep same idempotency key after a client timeout or double-click.
- **Template mode:** choose approved template and language available for that account; show its fixed text and required typed values, mapped from a permitted linked record or agent input. Missing, unsupported, paused or unmapped templates cannot submit. Start MVP with simple body-text parameters; explicitly disable unsupported header/button/component forms rather than generating partial payloads.
- **Timeline:** distinguish inbound/outbound and sender agent; show provider occurrence time with local display and absolute timestamp on inspection, captions, reply context and file download state. Show “Queued”, “Accepted by WhatsApp”, “Sent”, “Delivered”, “Read”, “Failed”, and “Outcome unknown” honestly. No blue ticks before receipts. Unknown inbound message types render a safe placeholder instead of disappearing.
- **Attachments:** preview name/type/size and upload progress, support removal before submission, and show downloading/unavailable/blocked states inbound. Store/download via authorized private File endpoints. Never render arbitrary message HTML; links are safe escaped links. Do not auto-download active content into browser previews.
- **Linked records:** right panel supports one or more explicit permitted Frappe links, such as Contact, Patient or Patient Visit. Opening/linking requires the business record's permission; viewing the conversation must not grant patient-record access. Avoid auto-linking people based only on a coincidentally equal phone number. Agent-visible previews exclude sensitive fields unless specifically authorized.
- **New conversation:** select permitted sender account and a valid peer/consented contact, then enter approved-template mode unless a reliable existing window is known. Consent/suppression is a separate eligibility check, not evidence of an open window.
- **Realtime and connection:** authorized post-commit events refresh the relevant row, messages and badges. A reconnect fetches deltas by cursor; events only hint at changes and are not the record of truth. Preserve drafts and show queued/connection states clearly. On mobile, list → thread navigation replaces the desktop columns; details open on demand. All actions have keyboard labels and error focus.

### Durable outbound path

1. Validate the request and persist the immutable message plus unique outbox intent in one database transaction. For document events, record source event identity and selected changed fields/safe rendered snapshot in that same business transaction. Delete events need their authorized snapshot captured before deletion.
2. Publish a job after commit. A periodic database dispatcher also finds ready intents so Redis outages after commit cannot lose work. Use the existing default/long queues unless the deployment explicitly adds dedicated workers; Compose currently consumes default, short and long.
3. A worker atomically claims one intent with a lease and records an attempt before network I/O. Commit the claim in a short transaction; do not hold database locks during HTTP. Recheck account enabled, suppression, window, template schema/approval, media ready/expiry and sender compatibility. Freeze the effective payload hash. Apply per-account/recipient pacing and bounded concurrency.
4. POST with explicit connect/read timeouts. Store provider message ID and accepted/held response atomically with the attempt outcome. Persist the originating agent and business record; never attach credential headers to jobs or logs. Where the pinned API contract supports an opaque callback correlation field, use a non-sensitive intent reference and test its callback behavior; do not treat that as provider idempotency.
5. Validation/auth failures become blocked/failed with actionable errors. Rate limits and explicit non-acceptance transient errors get bounded retries/backoff. A read timeout, worker crash after POST, lost response, or uncertain 5xx becomes Unknown until a status event or trustworthy reconciliation resolves it. Lease expiry after network start must not blindly resend. No general Cloud API delivery-status polling endpoint or historical webhook-fetch endpoint is assumed.
6. Return the existing logical request after duplicate client submissions; unique source-event/recipient/rule keys prevent duplicate automation expansion. A deliberate second message needs a new key. A campaign expands into bounded per-document/per-recipient intents so partial successes never require rerunning the whole campaign.

### Signed webhook ingress and asynchronous processing

1. GET verification checks mode/token and emits exact challenge text. POST reads bounded raw bytes, verifies the app-scoped signature, validates object/content envelope, and resolves the configured app/WABA/account. Signature verification is the narrowly scoped authentication substitute for this public route; keep Desk authentication and unrelated CSRF protection intact.
2. Store the signed receipt and normalized child events transactionally, then return HTTP 200 promptly. A known duplicate also gets 200. If durable storage fails, return a retryable failure; never acknowledge an in-memory-only job. Valid but unsupported event types are archived/acknowledged, while invalid signatures are rejected. Unknown accounts go to a restricted quarantine and alert, without creating arbitrary account records.
3. Handle every entry/change/message/status in a batch. Idempotent inbound processing upserts the `(account,peer)` conversation and `(account,wamid)` message under unique constraints, advances activity/window with provider time, applies the reopening rule, and schedules authorized attachment downloads. Replays do not increment unread twice. Future/skewed timestamps are bounded/quarantined rather than opening an unlimited window.
4. Status processing appends unique status events and updates a derived projection. Delivered/read must not regress when late sent events arrive; read can imply delivered. Keep failures and their timestamps as events rather than forcing every status into one numeric rank. Unknown/new provider statuses are retained. If receipts beat the send-response commit, retain them as unmatched and reconcile by provider ID/correlation later.
5. Post-commit realtime events carry only permitted identifiers/version/cursor hints to authenticated user/account/conversation rooms. Verify room access and revoke it when membership changes. Never broadcast all messages to a site-wide room. Browsers refetch through authorized APIs, recover gaps after reconnect, and dedupe by message ID/sequence.
6. A database sweeper retries event processing with bounded backoff; poison events go to an admin queue with replay controls. Deduplication retention must cover at least Meta's retry horizon plus a safety margin, and replay IDs must survive any longer retained raw-event archive. Messages retain their provider-ID uniqueness permanently within retention policy.

### Security, retention, and operations

Reuse the current role names where possible: Whatsapp Editor becomes an **agent** restricted to member accounts and permitted conversations; Whatsapp Admin becomes a **team supervisor** with assignment/bulk/template-rule management; a separate integration administrator/System Manager manages credentials and verified endpoints. Assignment filtering is a workflow feature unless product policy explicitly makes it an access restriction. All APIs/files/realtime must enforce whichever policy is selected.

Store private media and sensitive raw webhook payloads with restricted access and configurable retention. Keep operator errors short (Meta code, trace/correlation ID, redacted reason). No tokens, full recipient lists or patient content in Error Log by default. Preserve audit records for assignment, consent/suppression, retries, overrides and exports. Exact retention periods need product decisions; proposed MVP defaults are 30 days for raw events and 90 days for private media, with message-history retention explicitly configured before production rather than silently kept forever.

Monitor queue age, oldest due intent, expired leases, Unknown outcomes, failed/held sends, processing backlog/dead letters, unmatched receipts, webhook silence, account token/permission errors, storage growth and scheduler heartbeat. Show health separately from business delivery status: absence of callbacks is not proof that nothing was delivered. Database, private files, site config/encryption key, outbox and dedupe records must be backed up/restored together.

## Public webhook deployment for this home server

`frappe.home.arpa` and `192.168.10.62` are private/LAN addresses; Meta cannot call the current HTTP site. Outbound Graph API requests can originate from the LAN when configured, but incoming messages and delivery receipts require public HTTPS.

For a later authorized deployment, choose a real public hostname and either a managed HTTPS tunnel/reverse proxy or a small public ingress relay. Prefer exposing **only the webhook GET/POST route** to the Frappe frontend, keeping Desk, generic `/api/*`, files, database and Redis private. A public relay is an alternative when the LAN cannot accept inbound traffic; it must persist and authenticate forwarded events and define its own retry/dedupe contract. A VPN-only endpoint is insufficient unless Meta can reach it.

Terminate trusted TLS at the public edge, preserve the exact request body and signature header, route to the correct Frappe site, limit body size in line with Meta's documented 3 MB webhook payload bound, and use appropriate request/rate limits without breaking legitimate retries. Do not add interactive login or an access challenge to the callback route. Document the proxy trust/header configuration and monitor certificate/tunnel availability. Configure the WABA subscription and `messages` field, then verify challenge and signed test events. These are planned steps only; no DNS, tunnel, firewall, proxy, token or Meta dashboard changes were made.

The current stack already has websocket, scheduler and queue containers. That supports the proposed design, but healthy containers alone do not prove the site's scheduler is enabled, queue delivery works, or account events are subscribed. Verify those on staging, then production during an explicitly authorized rollout.

Audio/sticker have no captions. URL mode does not upload an empty file. Edited attachment invalidates/rebuilds upload. Files remain private. |

Concurrent agent assignment/status conflict visible. Draft retained on expiry/network failure; repeated send reuses request ID. Reconnect fills gaps without duplicates. **Recommended first implementation phase:** Phase 1, ending with reviewable code and disposable-site tests, while real dispatch remains disabled. Its goal is to make every send authorized, prevent secrets entering rendered messages, enforce enabled/recipient/template policy, and define truthful outcomes. Phase 2 should follow before building the interactive inbox against live traffic. A UI-only first change would leave the highest risks intact.

For rollout, use feature gates such as ingress capture, event processing, inbox visibility, outbox dispatch, and each automation trigger. Stop dispatch independently of webhook capture so a rollback does not lose incoming events. Avoid dual-send comparisons; shadow processing must never call Meta. Retain the previous image plus matching backup and schema compatibility notes; restore only through the deployment repository's controlled update process in a future authorized task.

## Product decisions and remaining questions

These do not invalidate confirmed defects; they determine implementation policy. Proposed defaults allow a first implementation specification without guessing production configuration.

| Decision | Proposed starting policy / question |
|---|---|
| Account/team access | Membership controls access; assignment is workflow only. Decide whether teams need assigned-only visibility. Supervisors can see their member accounts, integration admins manage credentials separately. |
| Peer/contact ownership | Portfolio-scoped peer with per-phone conversations; explicit trusted identity alias linking. Decide permitted Contact/Patient associations and whether shared family numbers require distinct record associations. |
| Consent and suppression | Record source/time/scope and honor suppression before every send. Decide the business owner and supported opt-out workflow; inbound contact alone must not be assumed to grant unrelated marketing permission. |
| Reopen / unread / read receipts | New inbound reopens Resolved; unread is per user. Do not send remote read receipts automatically in MVP. |
| Legacy records | Archive unknown sender separately. Decide any evidence-based mapping; do not fabricate historical delivery or inbound windows. |
| Templates and attachments | Start with approved body-text parameter templates plus inbound display and image/PDF sends. Disable unsupported components/types visibly. Decide which reminders/records actually need media headers later. |
| Bulk duplicates | Origin key includes source record/rule/occurrence and recipient. Decide whether business campaigns require one message per recipient across multiple source records; do not silently collapse genuinely distinct document notifications. |
| Schedules | Store UTC plus business timezone; skip and report missed occurrences by default. Decide any catch-up grace period or explicit bounded resend. |
| Hosting | Choose public hostname, managed tunnel versus relay, and availability/retention owner. No external endpoint was provisioned. |
| Retention / compliance | Approve history, raw-event, audit and private-file retention and who can export/delete. HMS patient-linked data makes these operationally important. Legal interpretation is outside this source review. |
| Account capability / pricing | Verify actual Meta app mode, permissions, account status, enabled BSUID/version behavior, limits and pricing at setup. No live token/phone/account inspection was performed. |
